# Trial: following the TDX getting-started procedure in a clean environment

Run on 2026-11-15 (the file is named for the planned trial day) by Claude, following
[`docs/build/tdx.md`, "Getting started"](../build/tdx.md#getting-started-from-nothing-to-a-verified-tdx-guest) as
committed at `a5c4306`, to find where a person with only the repository gets stuck. **The documents were not changed
during the trial**, so a person following them later stops at the same places and the two runs can be compared.

Every place where knowledge from outside the documents was used is recorded, including what was done without
thinking. Marks: **[outside]** knowledge not in the documents; **[stuck]** cannot go on as written; **[finding]** a
result the documents do not predict.

## Environment

- A **new** WSL 2 distribution, `attestamp-trial`, made with `wsl --install Ubuntu-24.04 --name attestamp-trial
  --no-launch` (WSL 2.7.14.0 accepts `--name`). Ubuntu 24.04.5 LTS. The existing `Ubuntu` distribution was not
  touched.
- **[outside]** `--no-launch` skips the first-run prompt that creates a user, so everything ran as **root**. A person
  installing WSL normally gets a user with `sudo`; the commands that start with `sudo` behave the same either way.
- Present out of the box: `git` 2.43.0. Absent: Go, `curl`, `openssl`, `gcloud`, `anvil`.

But `linux/att-ra-responder` came out as sha256 `a71bedfc…a186`, not the `5573b538…d668` the same commit gives on Windows. `go version -m` shows why: `CGO_ENABLED=1`. A native Linux build with a C compiler present (1.2) links with cgo; a cross-build from Windows or macOS does not. With `CGO_ENABLED=0` the same machine gives `5573b538…` exactly. **No document sets `CGO_ENABLED=0`, and `build` does not check it** (`internal/setup/build/responder.go` reads the Go version, `-trimpath`, VCS stamping, OS and architecture). For Nitro this is a measurement difference: a Vendor on Linux and an Auditor on Windows, both following the README, layer two different responders and get two different PCR0/PCR2. On TDX and SEV-SNP the responder is not measured, so it does not matter there |

### Step 6 Option 2 with the real tools (brief item 1.4)

Step 4's Option 2 packages were installed as written (`apt-get install -y squashfs-tools cryptsetup-bin`; versions in
`docs/build/toolchain.md`). **[outside]** WSL has no `/boot/initrd.img-*` and no kernel of its own to run
`mkinitramfs` for, so a stand-in base initrd was used. The image and its root hash do not depend on the base initrd;
the initrd's own hash does, and was not compared.

| build | result |
|---|---|
| `intel-tdx --option 2`, the document's `app/hello.txt` | built, `--verify` passed; root hash `5dff1f1d…643f` |
| `intel-tdx --option 2`, **[outside]** the recordings' one-file application (`app` holding `attestamp app v1`) | root hash `e29ec085…af0c9`, **the value measured on both guests on 2026-11-11** |
| `amd-sev-snp-verity`, the same v1 application | `app.img` `28bdfcff…ec1c`, root hash `e29ec085…af0c9`, PCR12 predicted `470379c7…4689`; `--verify` passed |
| `amd-sev-snp-verity`, the v2 application | `app.img` `b8e2656f…fb27`, root hash `a2f4df92…51e1`; `--verify` passed |
| the recorded `gcp-n2d-opt2-v1` evidence, read with `att-user ra-parse --at 2026-11-12T00:00:00Z` | `signature ok`, `nonce ok`, **PCR12 `470379c7…4689`**: the predicted value |

So the Go port of `make-verity-image.sh` gives byte for byte the images the guests made, and the PCR12 the build
predicts is the one the hook produced. Running the build as root (step 6 says `sudo`) was the trial's own case, so
whether `veritysetup format` also works as an ordinary user is still not known.
