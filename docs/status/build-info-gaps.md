# What the repository still lacks

What someone with only this repository still lacks to build, run and trust the project, and the design questions
that need a person's decision. Its pair, [test-matrix.md](test-matrix.md), says what is proven, and by what. The
record of the gaps that were filled or closed, and when, is
[`docs/results/build-info-gaps-2026-11.md`](../results/build-info-gaps-2026-11.md); the row numbers are the same in
both files.

"Needs" says who can fill a gap: **repo** (derivable from the repository or public sources), **person** (only
someone with the accounts or the original machines knows), **instance** (needs a running instance).

Closed 2026-11-17**: done in code, refused on an instance, and the new Nitro values taken (below) | measured 2026-11-16: `a9a45f2` added one function to `internal/cli`, which the responder imports but does not call, and the responder went from `5573b538…` (at `a9a45f2~1`) to `c61c988e…` (at `a9a45f2`); every recorded Nitro reference value became stale. The responder's dependencies are `internal/cli` and `internal/tee/request/...` (`go list -deps ./cmd/ra-responder`). Options to weigh, not tried: keep it as is and re-take the values whenever these packages change; give the responder its own minimal output code so that `internal/cli` can change freely; or something else. TDX and SEV-SNP are not affected (the responder is not measured there). *Investigated 2026-11-17 (no code changed; a decision is needed):* **What the responder uses:** one call, `cli.Errorln` in `cmd/ra-responder/main.go`, which prints its last error, in red when stderr is a terminal. No test depends on the colour. **Why an unused function changed the bytes: the Go build ID.** The linker drops unreachable code, but `go build` writes a build ID into the binary, a hash of every input package, so a change in any linked package changes the file even when no code that runs changed. Measured locally, linux/amd64, go1.26.1, `CGO_ENABLED=0 -trimpath -buildvcs=false`: the current responder `c61c988e…` (the recorded one); with one unused function added to `internal/cli` `bd2b4acf…`; the same two built with `-ldflags=-buildid=` (an empty build ID) **both** `215423b8…`. (2) drop `internal/cli` from the responder (a plain `fmt.Fprintln(os.Stderr, …)`): changes to `internal/cli` stop mattering, the others in (1) do not; the error is no longer red. (3) build the responder with an empty build ID (`-ldflags=-buildid=`): measured above, a change to code the responder never runs no longer moves its bytes, wherever it is; a change to code it can run still does (rightly: TDX and SEV-SNP extractors are reachable through `--extractor`). It is a fourth required build setting, which `build` would have to check like the other three (an empty build ID is readable with `go tool buildid`), and every document that lists the three. Not checked: whether an empty build ID affects anything else in the toolchain. (4) both (2) and (3). Any of (2)–(4) changes the responder's bytes once, so every Nitro reference value would be taken again, as after `a9a45f2`. A further option, not looked at: one responder per platform (build tags), so Nitro's would not carry TDX and SEV-SNP code. *Added 2026-11-17, same method:* even **comments** can move the bytes. Both were undone and `c61c988e…` rebuilt. So until this question is settled, documentation fixes must not touch `cmd/ra-responder` or the packages it links (`internal/cli`, `internal/tee/request/...`): two stale statements in `cmd/ra-responder/main.go` were left as they are for that reason (its first line says every role's build layers it into "the enclave image", which is Nitro only; it points at "internal/setup/build's entrypoint.sh", which `internal/setup/build/<role>/aws/build.go` writes), and so was its usage text ("every role's build layers this one binary as is"), which is a printed string and so certainly part of the bytes. *Decided and done 2026-11-17 (operator): (3).* The measurement showed that the build ID, not the code, moved the bytes, so (2) would not fix it, and (3) alone does; the dependency can stay. Go does not record `-ldflags` in a `-trimpath` binary's build info, so `build` reads the ELF note `.note.go.buildid`, which the linker leaves out when the ID is empty. **Measured first, 2026-11-17** (go1.26.1, linux/amd64 cross-builds from Windows, `CGO_ENABLED=0 -trimpath -buildvcs=false -ldflags=-buildid=`, at `da6bf36`): the responder `215423b8…`; a comment in `cmd/ra-responder/main.go` reworded without moving a line, `215423b8…` (**the same**); a comment appended after the last function, `215423b8…` (**the same**); a comment that turned one line into two, moving every line of code below it, `4913a62c…` (**different**: the binary keeps the line numbers of its code).
