# What the repository still lacks

What someone with only this repository still lacks to build, run and trust the project, and the design questions
that need a person's decision. Its pair, [test-matrix.md](test-matrix.md), says what is proven, and by what. The
record of the gaps that were filled or closed, and when, is
[`docs/results/build-info-gaps-2026-11.md`](../results/build-info-gaps-2026-11.md); the row numbers are the same in
both files.

"Needs" says who can fill a gap: **repo** (derivable from the repository or public sources), **person** (only
someone with the accounts or the original machines knows), **instance** (needs a running instance).

## Design questions to review

Not gaps in the documents and not decided here; each needs a person's decision.

| # | question | what is known | where |
|---|---|---|---|
| Q1 | **Should `att-ra-responder` link `internal/cli`?** On Nitro the responder is inside the measured EIF, so until the empty build ID any change to a package it links moved PCR0 and PCR2, even code it never runs. **Decided 2026-11-17: option (3), the empty build ID. Closed 2026-11-17**: done in code, refused on an instance, and the new Nitro values taken (below) | measured 2026-11-16: `1967749d` added one function to `internal/cli`, which the responder imports but does not call, and the responder went from `5573b538…` to `c61c988e…`. The cause was Go's build ID, not the code: built with `-ldflags=-buildid=` the responder was the same file with and without the function (`215423b8…`), so dropping `internal/cli` would not have fixed it. Every build now passes `-ldflags=-buildid=`, and `build` refuses a responder that carries a build ID (it reads the ELF note `.note.go.buildid`). Code the responder can run, and the lines that code sits on, still move its bytes, so a comment fix in `cmd/ra-responder` or a package it links must not move a line. Refused on an instance and new values taken at `83cb2dc` (`docs/results/aws-nitro-2026-11-17.md`). The options weighed, every measurement and the steps, in full: `docs/results/build-info-gaps-2026-11.md`, "Q1 in full" | `docs/build/ra-comparison.md`, "What covering the responder costs"; `docs/build/aws-nitro.md`, "The Go build ID, measured"; `docs/results/nitro-baseline-2026-11-16.md` |
| Q2 | **TDX: refuse an initrdless boot in the parser, as SEV-SNP does. Decided: yes, as the real fix, after publication, in a separate session.** | **Why the parser cannot do it today:** TDX evidence is the quote alone; the CC event log (CCEL) that shows whether GRUB loaded an initrd stays on the guest, so `internal/tee/parse/tdx` cannot tell an initrdless boot from what it receives (RTMR2 is one hash). SEV-SNP's parser can, because its evidence is a container whose vTPM attestation carries the event log. **The real fix:** make `intel-tdx` a container (quote + CCEL), like SEV-SNP's, move the replay from `internal/setup/launch/tdx` into `internal/tee/parse/tdx`, and refuse in `Parse`. **Cost:** a wire-format change; the `gcp-c3-*` fixtures re-recorded (one TDX guest); the e2e tests changed; and every TDX result so far (the three-platform comparison, [D3](../results/trial-2026-11-16-clean.md#every-difference-found), [the clean trial](../results/trial-2026-11-16-clean.md)) was measured on today's format, so TDX is run again. **Done meanwhile (2026-11-16):** `audit` refuses a CVM format without `--build-measurements`, and the same day on every platform (`fix(cmd/auditor): require --build-measurements for audit on every platform`) (`fix(cmd/auditor): refuse to audit …`); measured before and after in `docs/results/sessions-2026-11-16/tdx-initrdless.md`: the path by which an initrdless boot became `trusted` is closed. **Not closed:** `register` by hand with such values (an Auditor vouching for what it did not build) | `internal/tee/parse/snp/measure.go`; `internal/setup/launch/tdx/check.go` |
| Q3 | **What should `audit --vendor-tee` exit with when the Vendor's TEE runs something else? Decided and done 2026-11-16: exit 12** (`fix(cmd/auditor): exit 12 when --vendor-tee …`), after registering, with a message that the registration succeeded, only the Vendor comparison failed, and not to run it again (exit 5). Chosen while there are no outside users, since an exit code becomes part of the interface once published; not (c), because the Auditor vouches for its own build, not for the Vendor's deployment | Options that were weighed: (a) keep 0 and document it; (b) a new code after registering (chosen); (c) do not register when the Vendor differs; (d) an opt-in flag. `flow1/1 -v` treats 12 as registered and goes on; `flow2/4` reads 12 as its expected verdict | `docs/results/audit-2026-11-12.md`, finding 3 |
| Q4 | **Drop `internal/cli` from `att-ra-responder`** (option (2) of Q1). **Decided 2026-11-17: after publication, not now.** The reason is no longer reproducibility (the empty build ID settled that, Q1) but **less code inside the measured EIF**: whatever the responder links is part of what a Nitro User trusts, and `internal/cli` is there for one call, `cli.Errorln`, which prints the last error in red | the responder would print its error with `fmt.Fprintln(os.Stderr, …)`; its bytes change once, so the Nitro reference values are taken again (any change to code the responder can run does that). The same reasoning covers the other option Q1 named and did not try: one responder per platform (build tags), so Nitro's would not carry TDX and SEV-SNP code | `cmd/ra-responder/main.go` |
| Q5 | **The base initrd on TDX and SEV-SNP: keep taking the Vendor's binary?** On Nitro the Auditor rebuilds everything from source, which is the project's central claim. On a confidential VM the distribution base initrd is not reproducible (`mkinitramfs` and `dracut` write a random seed), so for Option 2 today the Auditor takes the Vendor's published base initrd and reproduces only the application part (for Option 1 both use the image's own initrd, the same file on every guest of one image; `STRUCTURE.md`, "Build and launch on the three platforms"). That weakens the Auditor's independence. Two other ways, neither tried: **(b)** build a reproducible base initrd ourselves, which keeps the claim and is much more work; **(c)** put the kernel and initrd into the launch measurement itself: `sev-snp-measure` accepts `--kernel`, `--initrd` and `--append`, so the path exists in principle, but **whether GCP lets a tenant launch that way is unverified**. If (c) worked on SEV-SNP, the vTPM, and with it the same-VM problem (T10), would no longer be needed | today's way works and is what the two procedures and the recorded fixtures use. Prior work on the SEV-SNP side, only the abstracts read: V. Narayanan et al., "Remote attestation of SEV-SNP confidential VMs using e-vTPMs", ACSAC 2023 (arXiv:2303.16463, doi:10.1145/3627106.3627112), a vTPM inside the SEV-SNP trust boundary; L. Wilke and G. Scopelliti, "SNPGuard: Remote Attestation of SEV-SNP VMs Using Open Source Tools", SysTEX 2024 (arXiv:2406.01186), the whole boot chain attested without a vTPM. Whether either binds a vTPM quote into an SNP report's report data is unchecked | `docs/build/tdx.md`, `docs/build/sev-snp.md`; `docs/build/ra-comparison.md` (T10) |
| Q6 | **How the shared boot files travel between the Vendor and the Auditor.** On a confidential VM the Auditor needs the Vendor's base initrd today, and with Q5 (b) or (c) the kernel and disk image too. `core/transfer` moves JSON and one image file through git; whether that is enough for these files, or a separate store is needed, is open | today the Option 2 base initrd is copied with `gcloud compute scp`, step A2 of "The Auditor's half" in both procedures | `internal/core/transfer` |
| Q7 | **A way to ask the Vendor's TEE without registering?** `audit --vendor-tee` compares the Vendor's TEE with the Auditor's build only as part of an audit, which registers the Auditor's value. On a registry that already holds that value the audit stops at exit 5 ("already registered"), after the comparison but before it can report exit 12. So there is no way to check the Vendor again later, on the registry the Users are pointed at. **To review after publication; not changed now** | `e2e/cvm/flow1-auditor-registers/2b-…` and `4b-…` deploy a registry of their own each run only to get a clean audit with `--vendor-tee`; the registry is used for nothing else. Harmless for a demonstration, odd for anyone using the repository. Options, not weighed: a flag that compares and does not register; `compare` with the Vendor's TEE address (today it takes measurements or a record key); or `audit` that treats "already registered with the same value" as done and goes on to the Vendor comparison | `cmd/auditor/audit.go`; `e2e/README.md`, "Flow 1 on TDX and SEV-SNP" |
