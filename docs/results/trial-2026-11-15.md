# Trial: following the TDX getting-started procedure in a clean environment

Run on 2026-11-15 *(the file was named for the planned trial day, `trial-2026-11-16.md`, and renamed to the day it ran on 2026-11-18)*, following
[`docs/build/tdx.md`, "Getting started"](../build/tdx.md#getting-started-from-nothing-to-a-verified-tdx-guest) as
committed at `d469e12`, to find where a person with only the repository gets stuck. **The documents were not changed
during the trial**, so a person following them later stops at the same places and the two runs can be compared.

Every place where knowledge from outside the documents was used is recorded, including what was done without
thinking. Marks: **[outside]** knowledge not in the documents; **[stuck]** cannot go on as written; **[finding]** a
result the documents do not predict.

## Environment

- A **new** WSL 2 distribution, `attestamp-trial`, made with `wsl --install Ubuntu-24.04 --name attestamp-trial
  --no-launch` (WSL 2.7.14.0 accepts `--name`). Ubuntu 24.04.5 LTS. The existing `Ubuntu` distribution was not
  touched.
- **[outside]** `--no-launch` skips the first-run prompt that creates a user, so everything ran as **root**. A person
  installing WSL normally gets a user with `sudo`; the commands that start with `sudo` behave the same either way.
- Present out of the box: `git` 2.43.0. Absent: Go, `curl`, `openssl`, `gcloud`, `anvil`.

### The disk UUID question (brief item 2.3), measured

| | `attestamp-tdx-vendor` (made 2026-11-10) | `attestamp-tdx-auditor` (made 2026-11-15) |
|---|---|---|
| image | `ubuntu-2404-noble-amd64-v20261105` | the same |
| root file system UUID | `9d4d258d-90ac-4d94-b296-007fa0812719` | **the same** |
| stock `GRUB_FORCE_PARTUUID` | `27c09ec4-48e8-4dfd-be36-678080b236c7` | **the same** |
| stock base initrd | `4703ec07…b0a2` | **the same** |
| command line with our entry | `… root=UUID=9d4d258d… ro console=ttyS0,115200` | **the same** |
| Option 1 initrd built from `app/hello.txt` | sha384 `bc024887…c43b` | **the same** |
| MRTD, RTMR0, RTMR1 | `f21e6b48…`, `8847ec5d…`, `6e1a3f88…` | **the same**, and equal to the 2026-11-11 recordings |
| RTMR2 after the same launch | `0f36ec64…` | **the same** |

**The UUIDs belong to the image, not to the disk.** Every disk made from one image version carries the same file
system UUID and partition UUID, so the command line, and with it RTMR2, is the same on every guest of that image.
Two guests built the same application into the same initrd and measured **the same four values**: an Auditor
rebuilding on its own guest gets exactly the Vendor's registered values. What can still change them: another image
version (the family moves), another kernel, another machine type (RTMR0 is expected to follow the VM shape; both
guests here are `c3-standard-4`). So both sides have to pin the **exact image**, not the family.

### CMDLINE on two SEV-SNP guests

The older guest built the same `app/hello.txt` from its own `/boot` base initrd (`4703ec07…`, the same file) and
launched it: **MEASUREMENT, PCR4, KERNEL, CMDLINE and INITRD were all equal** to the new guest's (CMDLINE
`80dfd7d3…`, INITRD `11cd710e…`). The same conclusion as TDX: the root UUID in the command line comes with the image,
so on one image version an Auditor's own build matches the Vendor's registration.

## What this trial found, in one place

| | finding | kind |
|---|---|---|
| 1 | Step 1 runs a script from the repository before step 2 clones it | procedure order |
| 2 | `gcloud` and `anvil` have no install command (`foundryup --install v1.8.0` was outside knowledge) | missing instruction |
| 3 | The documented clone URL holds an older tree until these commits are pushed | publishing |
| 4 | **`att-ra-responder` differs with cgo**: on Linux with gcc the README's build gives `a71bedfc…`, cross-builds give `5573b538…`; `CGO_ENABLED=0` is set nowhere and `build` does not check it. Matters for Nitro measurements | reproducibility bug |
| 5 | After `launch --reboot`, "wait a minute" was not enough once: the old boot was still up | procedure wording |
| 6 | TDX step 13: `rmdir /opt/app-verity` before the reboot fails (still mounted) | procedure order |
| 7 | `gcp-cvm.sh stop` with two guests fails on Windows (carriage return in the names) | script bug |
| 8 | `pkill -f` in a one-line remote command kills its own shell (harness only; not a person typing) | trial artefact |

**Confirmed working on real guests, for the first time:** `launch` install and `--check` on TDX and SEV-SNP, both
options; the responder answered another machine; `audit` and `verify` passed from another machine; the undo returned
both guests to the stock boot. **Measured:** the disk UUIDs, the base initrd and therefore the command line come with
the image, so two guests of one image give the same registered values.
